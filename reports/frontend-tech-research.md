# Sentinel frontend: techniques and advances beyond CSS (12 Nov 2026)

Read-only research. No code, tests or configs were changed. Written for the main frontend session.

**Source quality key.** Every claim has a URL. **(official)** = framework, standards or vendor documentation. **(secondary)** = a mirror, news item or practitioner write-up. **(weak)** = SEO listicle, aggregator or vendor-adjacent comparison; used only for direction, never for numbers I depend on. Where my searches returned a mirror instead of the primary page, I say so. I did not fetch pages in full, so version numbers and sizes below are as the search summaries reported them and should be re-checked before they drive a decision.

**What I found in our code (facts for the recommendations):**
- `frontend/package.json`: Next 16.2.3, React 19.2.4, SWR 2.3, axios, zustand, leaflet, react-simple-maps, lucide-react, vitest 4.1. `dev` is `next dev --webpack`; `build` is plain `next build` (Turbopack is the default bundler in 16 per the release post below, but `next.config.ts` carries a `turbopack.root` and the dev script forces webpack). No `reactCompiler`, no `cacheComponents`, no bundle analyzer, no Playwright, no Testing Library, no jsdom, no direct Zod dependency (a `zod` copy exists in `node_modules`, apparently transitive; confirm with `npm ls zod` before relying on it).
- App shape: 145 files carry `'use client'`, 91 files call `useSWR`, 96 component files, 15 `dynamic()` calls. Dashboard pages are `app/(dashboard)/*` with a shared `layout.tsx`, `loading.tsx` and `template.tsx`.
- Live data: `lib/liveStream.ts` (one shared socket per tab, 300-event ring, `FLUSH_MS = 250`, reconnect 1 s to 30 s backoff, 5 s idle close, a position-report dedupe).
- Service worker: `public/sw.js` caches only `/_next/static/*`, `/icons/*` and `/offline.html`; never pages or `/api/*` (deliberate, documented in the file).
- Security: `next.config.ts` sets a CSP with `'unsafe-inline'` and `'unsafe-eval'` on `script-src` and `connect-src 'self' ws: wss:`; `/sw.js` is `no-cache`.
- Deploy: `Dockerfile` is a 3-stage node:20-alpine build using `output: "standalone"`, but installs with `npm install --legacy-peer-deps` (not `npm ci`).
- Accessibility today: only 8 `aria-live` regions in the whole app. One is on the candle chart's hover readout (`CandleChart.tsx:126`), which changes on every pointer move.
- `components/ui/DataGrid.tsx` (202 lines) has no `role="grid"`, no `onKeyDown`, no roving tab index (my grep found none).

## Part B: Charting decision (hand-written SVG vs lightweight-charts vs uPlot vs visx)

**Sizes (conflicting; measure in our build with the analyzer before deciding):**
- lightweight-charts v5: the vendor says the base bundle is about 35 kB after a 16% reduction (official post, does not say gzipped): https://www.tradingview.com/blog/en/tradingview-lightweight-charts-version-5-50837 . Registry listings report about 172 KB minified and 54 KB gzipped for v5.0.8 (secondary/weak): https://depscope.dev/pkg/npm/lightweight-charts .
- uPlot: about 45 to 50 KB minified (npm README, official): https://npmjs.com/package/uplot ; the package is MIT licensed per the same README.
- visx: a set of packages; not measured.
- Our own cost today: zero for candles (about 256 lines in `CandleChart.tsx` plus `lib/candles.ts`).

**Licence cost of lightweight-charts.** It is Apache-2.0 (npm listing, secondary). Secondary sources say users must show TradingView attribution (an `attributionLogo` option and a NOTICE requirement) and I did not read the NOTICE text: https://www.npmjs.com/package/lightweight-charts . This is a real obligation to read before adoption.

**Our rules.** `CLAUDE.md` says free data only and "no new third-party packages when the standard library or existing dependencies suffice." A chart library is not strictly needed for the current charts, so adopting one needs a stated reason and the owner's agreement.

**Recommendation.**
1. Keep hand-written SVG while a chart has fewer than about 1,000 marks (3 nodes per candle means about 330 candles). Add a performance test: render time for 300 and 1,000 bars under 16 ms in the Profiler.
2. If dense intraday charts are needed, first try a small **canvas layer for the bodies only** inside the existing `CandleChart` (hand-written, about 60 lines) and keep SVG for axes, crosshair and labels; that avoids a dependency and keeps the text alternative.
3. Only if both fail (pan/zoom over tens of thousands of bars, drawing tools, tick-by-tick append), adopt lightweight-charts for the candle chart, behind a `dynamic()` import, with attribution handled and a Playwright screenshot test. Measure the added gzipped bytes first and set a budget (Part C).
4. uPlot only for very dense line series. visx is not worth adding.

Evidence is weakest on real-world sizes and on how lightweight-charts behaves under our theming and accessibility needs; prototype one chart to answer that.

2. **Fix screen-reader noise and the keyboard model:** remove `aria-live` from the candle hover readout, add one throttled `role="status"` announcer, add arrow-key navigation to chart and grid (4.1 to 4.3, S to M).
3. **Generated API types from the FastAPI schema plus Zod/Valibot on the five highest-stakes routes** so a field rename cannot show a wrong number (5.4, 5.5, M).
4. **Visible connection and data age everywhere:** socket state (Live / Reconnecting / Delayed), "as of" age on each polling panel, hidden-tab pause for polling and flush (2.1, 2.3, 2.5, 2.6, S to M).
5. **Playwright + axe smoke suite in dark and light:** the first real accessibility and visual regression net (5.1, M).
6. **Nonce-based CSP, Report-Only first, then enforce;** also decide on Trusted Types after grepping for HTML sinks (6.1, 6.2, M).
7. **React Compiler, behind a before/after profile** (1.2, M).
8. **Docker hygiene:** `npm ci`, check why `--legacy-peer-deps` is needed, `.dockerignore`, nginx caching for `public/` (6.3, 6.4, S).
9. **`useTransition` for search, palette and frame changes** (1.5, S).
10. **Dev-only `/kit` route** that renders every component state, captured by Playwright (5.3, S).

Next candidates: virtualised tables (if a measured list exceeds about 500 rows), Turbopack dev (1.8), documented `http://localhost` dev setup (6.5).

## Three things NOT worth doing

1. **Rewriting the live feed to SSE or adding TanStack Query.** The shared WebSocket and 91 SWR hooks work and are tested; the gain is small and the sources recommending SSE (all weak) describe a different situation (one-way pushes with no existing socket).
2. **Moving everything to server components and Cache Components now.** Our pages are per-user behind a session proxy, a nonce CSP forces dynamic rendering anyway, and 145 client files would need reshaping. The risk of leaking per-user data into a shared cache outweighs the shell savings.
3. **Web Workers and OffscreenCanvas, or adopting visx/Storybook.** Nothing measured shows a main-thread problem that a worker would solve, visx duplicates what the hand-written SVG already does, and Storybook adds a large dev tree where a `/kit` route suffices.

## Weak evidence and open checks

- Sizes for lightweight-charts and TanStack Virtual conflict between sources; measure in our build.
- No react.dev page was returned for the React 19 hooks; all hook descriptions are from practitioner articles.
- I found no authoritative source on screen-reader behaviour for fast-changing prices; the "silent ticker, announce events" pattern is my inference and needs a real screen-reader test (NVDA, VoiceOver).
- Trusted Types support dates conflict (Firefox 139 vs 148).
- SWR option names, `Last-Event-ID` behaviour, and Playwright's `animations: 'disabled'` option should be confirmed on their own documentation before coding.
- The reason `dev` uses `--webpack` is not documented in what I read; ask the frontend session before removing it.
